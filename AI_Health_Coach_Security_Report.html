1. Project Overview

The AI Health Coach is an AI-powered health, fitness, recovery, and lifestyle coaching platform. It connects to wearable data and user-entered data to generate personalized insights, coaching, workout plans, and nutrition guidance.

Core Capabilities

  • User authentication (email/password with bcrypt)
  • Health/fitness profile management (age, height, weight, goals, activity level)
  • Wearable integrations (Fitbit, Google Fit, Garmin, Apple Health) via OAuth
  • Health metrics ingestion (steps, heart rate, sleep, calories, blood oxygen, HRV, respiratory rate)
  • Native workout logging (exercises, sets, reps, weight, duration, progressive overload)
  • Meal/nutrition logging (macros, meal types, descriptions, photo uploads)
  • AI coaching chat with streaming responses (OpenAI GPT-4o-mini)
  • Progress tracking with 30-day summaries and metric trends

Sensitive Data Handled

  • Account credentials & session tokens
  • Personal profile data (age, sex, height, weight)
  • Health/fitness metrics from wearables
  • Nutrition/diet data
  • Workout history
  • AI conversation history
  • OAuth tokens for third-party integrations

4. Rate Limiting Implementation

Rate limiting uses an in-memory sliding-window algorithm with 7 sensitivity tiers. Each tier has a namespace prefix to isolate counters. The implementation is Redis-upgradeable — same API surface.

TierLimitWindowKey StrategyEndpoints Protected
auth560sPer-IPSignup, login, password reset
ai2060sPer-User + Per-IP (dual)AI coaching chat
general6060sPer-User:IPDashboard reads, lists, profile GET
mutation3060sPer-User:IPCreate/update/delete operations
upload1060sPer-User:IPPhoto/file uploads
wearableSync1060sPer-User:IPWearable data sync
webhook3060sPer-IPOAuth callbacks

429 Response Format

{ "success": false, "error": "Too many requests. Please try again later." } Headers: Retry-After: <seconds> X-RateLimit-Limit: <max> X-RateLimit-Remaining: 0 X-RateLimit-Reset: <timestamp>

Key Design Decisions

  • AI endpoints use dual rate limiting (per-user AND per-IP) to prevent both individual abuse and distributed attacks
  • Auth endpoints rate limit by IP only (user not yet authenticated)
  • All other endpoints combine user ID and IP for the rate limit key
  • RATE_LIMIT_ENABLED env flag allows disabling in development/testing
  • Expired entries are garbage-collected every 60 seconds to prevent memory leaks

Body Size Protection

  • Middleware level: Next.js server actions body limit set to 1 MB
  • Application level: parseBody() checks Content-Length header and rejects bodies > 1 MB
  • Upload level: Configurable via UPLOAD_MAX_SIZE_MB env var (default 5 MB)

6. Secret Handling

Principles

  • ✓ All secrets in .env / .env.local — never committed to source control
  • ✓ .gitignore excludes all .env* files except .env.example
  • ✓ .env.example contains only placeholder values
  • ✓ No secret has the NEXT_PUBLIC_ prefix — never bundled into client-side JavaScript
  • ✓ env.ts validates all required secrets at startup; crashes in production if missing
  • ✓ iOS client contains zero embedded secrets — communicates with API over HTTPS
  • ✓ Error responses never include secret values, provider names, or stack traces
  • ✓ Console logging never includes secret values

7. OWASP Hardening

OWASP CategoryControl ImplementedStatus
A01 — Broken Access Control Every resource endpoint checks userId === session.user.id. Returns 404 (not 403) on ownership failures to prevent IDOR enumeration. Done
A02 — Cryptographic Failures Passwords hashed with bcrypt (cost 12). JWT signed with NEXTAUTH_SECRET (≥32 chars). HSTS enforced (2 years). Done
A03 — Injection Prisma ORM prevents SQL injection. Zod validates all inputs. HTML tags stripped from user strings. Filenames sanitized. Done
A04 — Insecure Design Server-side validation mandatory. Client-side validation is supplementary only. All schemas use .strict() to reject unknown fields. Done
A05 — Security Misconfiguration Security headers via middleware (CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy). Content-type enforcement on mutation routes. Done
A06 — Vulnerable Components Minimal dependency footprint. Production dependencies: 8 packages. All well-maintained. Done
A07 — Auth Failures Rate-limited auth (5/min). Generic error on duplicate email prevents user enumeration. Session maxAge: 30 days. Done
A08 — Data Integrity Failures Zod schemas enforce data shape. Prisma enforces DB constraints. Wearable OAuth state token generated (verification TODO). Partial
A09 — Logging Failures Errors logged server-side with safe messages. No secrets logged. Request IDs generated in middleware for tracing. Done
A10 — SSRF No user-controlled URLs used in server-side fetches. OAuth URLs built with validated enums and URLSearchParams. Done

Issues Found & Fixed During Adversarial Review

  1. CSP script-src broke Next.js hydration — Nonce-based CSP blocked inline scripts. Fixed: relaxed to 'unsafe-inline' with upgrade path documented.
  2. RATE_LIMIT_ENABLED env var unused — Flag was defined but never checked. Fixed: integrated into rate limiter check() method.
  3. parseBody had no size guard — Could accept arbitrarily large bodies. Fixed: added 1 MB Content-Length pre-check and post-read length check.
  4. Unused import in signup route — NextResponse imported but not used. Fixed: removed.
  5. OAuth URLs built via string concatenation — Potential parameter injection if env vars contain special chars. Fixed: migrated to URL + URLSearchParams.
  6. Unused import in upload route — NextResponse imported but not used. Fixed: removed.

Manual Verification Required

  • Set up PostgreSQL and run npx prisma db push
  • Configure .env.local with real values
  • Run npm run dev and verify web app startup
  • Open iOS project in Xcode and verify compilation
  • Test full auth flow: signup → login → dashboard
  • Test AI chat with a real OpenAI API key
  • Verify rate limiting triggers correctly (send 6+ rapid requests to signup)
  • Verify validation rejects malformed payloads (send extra fields, out-of-range values)

12. Recommended Next Steps

  1. Redis-backed rate limiting — Replace in-memory Map with @upstash/ratelimit for multi-instance deployments.
  2. Wearable token encryption — Encrypt OAuth access/refresh tokens at rest before storing in the database.
  3. OAuth state verification — Store state tokens in Redis/DB with short TTL; verify on callback to prevent CSRF.
  4. CSRF token protection — Add CSRF token verification for non-NextAuth mutation routes.
  5. Nonce-based CSP — Upgrade to Next.js experimental CSP nonce support when stable.
  6. Structured logging — Add pino or winston for structured request logging with request IDs.
  7. API integration tests — Add tests for auth, validation, rate limiting, and ownership checks.
